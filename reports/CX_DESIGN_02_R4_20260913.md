## Support: actual local delivery

The existing SQLite stack and /admin/support-center now receive authenticated
support messages in the additive nemesis_support_requests table. No commercial
DB, account schema or production data was accessed. No new service or SMTP use.

Success is returned only after commit, followed by POST/redirect/GET. The receipt
says received in the support inbox, not reviewed, replied to or emailed.
An administrator reads the same stored message; a client cannot read the inbox.
GET uses a read-only database connection, and creates no table.

Controls: existing CSRF/auth, session request ID, idempotent receipt, transaction
rollback, escaped user content, length/category validation, persistent per-user
60-second and three-per-hour limits. Explicit credential assignments are rejected;
the UI tells users not to include credentials. This is not a universal secret
detector: support bodies are user content and require restricted staff handling.
No message body, credentials or email is written to application logs by this code.

Permanent tests cover persistence/admin visibility, repeated receipt, user isolation,
rate limits, invalid fields, credential rejection, escaping and insertion failure.
Browser covers client submit -> committed receipt -> refresh -> admin reads same
message on desktop and mobile, plus CSRF rejection and client/admin separation.
SUPPORT_DELIVERY_VERIFIED = PASS_LOCAL; OPEN_FUNCTIONAL_P1 = 0 in reviewed scope.
Production rollout, notifications, staff response/resolution workflow and retention
policy operation are NOT_TESTED. Inbox receipt is not a promise of human response.
