# Guía de microcopy de NeMeSiS SHARK PRO

## Objetivo

Toda frase visible debe ayudar al usuario o al administrador a entender qué ocurre, qué puede hacer y qué nivel de confianza tiene la información. La copia debe sonar profesional, breve y natural.

## Voz

- Clara: una idea por frase.
- Premium: sobria, segura, sin exagerar.
- Honesta: si falta información, se dice.
- Responsable: no promete ganancias ni resultados.
- Útil: cada texto debe orientar una acción o explicar un estado.

## Principios

1. Datos reales antes que abundancia.
2. Transparencia antes que apariencia.
3. Calidad antes que cantidad.
4. Acción clara antes que decoración.
5. Castellano natural antes que traducción literal.

## Cliente

El cliente no debe ver jerga interna si no aporta valor. Se prefiere:

- "No disponible" cuando falta un dato.
- "Información pendiente" cuando el sistema aún no puede confirmar.
- "Solo datos confirmados" cuando se explica un filtro.
- "Revisar picks" en lugar de etiquetas técnicas.
- "Abrir SHARK" cuando la acción lleva al centro de inteligencia.

Evitar:

- Nombres internos de motores.
- Estados sin contexto.
- Mayúsculas completas salvo siglas o marca.
- Promesas como "ganar", "asegurado", "garantizado" o "sin riesgo".

## Administración

El administrador puede ver lenguaje operativo, pero debe seguir siendo comprensible:

- "Centro de operaciones" para vista global.
- "Preparación de producción" para readiness.
- "Salida a producción" para go-live.
- "Evidencia" para pruebas o soporte.
- "Actualización" para frescura del dato.

Evitar:

- Mezclar inglés y español en el mismo bloque.
- Mostrar nombres técnicos si existe una forma funcional clara.
- Acciones ambiguas como "Run" o "Check" sin explicar el resultado.

## Botones

Los botones deben ser verbos o acciones claras:

- Abrir calendario
- Ver partido
- Revisar picks
- Consultar SHARK
- Exportar informe
- Ejecutar revisión segura
- Generar prompt Codex
- Volver al calendario

Evitar botones que solo nombren una tecnología cuando la acción no es obvia.

## Estados

Usar siempre estados honestos:

- Confirmado
- Parcialmente verificado
- No certificado
- Bloqueado por acceso
- Datos insuficientes
- No disponible
- Pendiente de revisión

No usar "OK" para información que no ha sido probada.

## Fechas, horas y moneda

- Hora visible: Madrid cuando aplique.
- Fecha visible: formato legible en castellano.
- Moneda: formato español y símbolo claro.
- No mostrar ISO salvo en paneles admin, API o diagnóstico.

## Mensajes de error

Un buen error debe decir:

- qué ha ocurrido;
- si afecta al usuario;
- qué puede hacer ahora;
- si el equipo ya puede investigarlo.

Ejemplo recomendado: "No se pudo cargar esta información. Puedes reintentarlo o volver al calendario."

## Mensajes vacíos

Un estado vacío debe ser Útil:

- "No hay picks publicables con datos completos."
- "No hay partidos en directo confirmados."
- "No hay suficiente información para calcular este contexto."

Evitar estados vacíos decorativos o silenciosos.

## Regla permanente

Si una pantalla necesita explicar la interfaz con demasiado texto, el problema probablemente es de experiencia, no de microcopy.
