# NeMeSiS X Dependency Map

## Executive Summary

**The dependency map confirms one controlling fact: NeMeSiS X depends on `LRM-001`.** No future product expansion should begin until production readiness, operational evidence, Telegram, Stripe, restore, observability, Browser QA, Sentinel, Privacy and Secret Guard are certified.

**The future product is a chain, not a menu.** Sports intelligence requires compliant sources, canonical entities, evidence contracts, graph relationships, user consent and operational monitoring.

---

## 1. Master Dependency Chain

```text
LRM-001 Release Gates
-> Closed Beta
-> Real Usage Evidence
-> Release 1.x Commercial Discipline
-> Sports Intelligence Expansion
-> Daily Companion
-> Intelligence Network
-> Scale Platform
```

If any upstream block is missing, downstream initiatives remain blocked or design-only.

## 4. What Must Not Start Before LRM-001

The following initiatives must not start before `LRM-001` is closed:

- closed beta with real users;
- public Release 1.0;
- new sports modules;
- new data sources;
- Telegram expansion beyond controlled certification;
- Stripe commercialization;
- advanced picks;
- bankroll expansion;
- Live Center expansion;
- distributed SHARK;
- AI assistant;
- community launch;
- international expansion;
- high-scale infrastructure changes not required to close `LRM-001`.

Allowed before `LRM-001` closure:

- documentation;
- read-only certification;
- QA;
- release gate evidence gathering;
- support/runbook cleanup;
- risk documentation;
- no-code product planning.

## 5. Dependency Risks

| Risk | Dependency failure | Consequence |
|---|---|---|
| Premature beta | Production or restore not certified | Real users hit preventable failures |
| Premature Telegram | Gate 3 not PASS | Spam, wrong destination or unverified delivery |
| Premature monetization | Stripe not certified | Payment/member mismatch |
| Premature sports expansion | Source compliance missing | Legal and data-quality risk |
| Premature AI | Evidence graph immature | Hallucination and trust failure |
| Premature scale | Observability incomplete | Failures become invisible |

---

## 6. Dependency Rule

An initiative may move from design to LRM execution only when:

1. its upstream dependencies are PASS or explicitly accepted as risk;
2. it has a stable LRM ID;
3. it does not bypass `LRM-001`;
4. it has user or production evidence when required;
5. it preserves canonical architecture;
6. it has QA, Sentinel, Privacy and Secret Guard validation plan.
